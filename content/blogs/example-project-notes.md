一个小工具的起点，往往不是复杂的技术方案，而是一句很简单的话：这件事情，能不能少做一遍？

这篇文章以一个虚构的文件整理工具为例，展示项目复盘的写法。重点放在决策过程，而不是最终用了多少技术。

## 先把问题说清楚

假设每周都需要把一批文件按日期归档。文件来自不同渠道，命名规则也不一致。每次整理都包含三个重复动作：打开文件、判断日期、移动到对应目录。

在开始写代码之前，可以先记录三个问题：

- 哪一步最耗时？
- 哪一步最容易出错？
- 哪些情况必须由人来判断？

> 自动化的第一步，是明确哪些事情值得自动化，以及哪些决定应该留给人。

## 把过程拆成小步骤

第一版只需要完成一条可检查的流程：读取文件名，生成整理建议，再由使用者确认。

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| 收集 | 一个指定文件夹 | 文件清单 |
| 分析 | 文件名与日期规则 | 目标目录建议 |
| 预览 | 整理建议 | 待确认列表 |
| 执行 | 已确认列表 | 操作记录 |

与其一开始就自动移动所有文件，不如先输出一份预览。这样既能发现规则遗漏，也能避免错误操作。

## 第一版可以很小

下面的示意代码只生成目标路径，不执行文件移动：

```python
from pathlib import Path

def suggest_destination(filename: str, year: int, month: int) -> Path:
    safe_name = Path(filename).name
    return Path("archive") / f"{year}-{month:02d}" / safe_name

print(suggest_destination("notes.md", 2026, 9))
```

一个可用的第一版，应该能够走完主要流程，也应该明确告诉使用者它还不能处理什么。

## 复盘时记录什么

项目完成后，值得留下的往往是这些细节：为什么选择先做预览、哪条规则被推翻过、什么输入让程序出现了意外。

这些记录会让一个项目从“做过”变成“能够讲清楚”。后续再遇到相似问题时，也不必从头摸索。
